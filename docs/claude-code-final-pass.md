# Claude Code final release prompt

You own the final release of TRACE, a Next.js and TypeScript reference manager and evidence-review app. This build will be shared with the hackathon group after deployment. Audit it, fix reproducible bugs that affect users or deployment, and verify the finished release. Work from the current working tree and preserve the existing changes.

1. Read `PRODUCT.md`, `DESIGN.md`, `docs/submission-audit.md` and `docs/submission-checklist.md`. Inspect the patch, app routes and provider integrations, test coverage, project storage, reviewed export, and production configuration. Use the organiser requirements already recorded in the repo. Keep credentials and private documents out of prompts, logs, Git, build artifacts, and browser uploads.
2. Reproduce and fix any defect that can lose work, mislabel sample output, let an unresolved citation pass reviewed export, expose private data, or stop a judge from completing the main journey. Check browser storage and backup recovery, overlapping edits in separate tabs, provider failures, API quota behavior, and citation formatting in APA 7 and Harvard. Keep the light UI, visible citation trap, and current architecture. Avoid new features that do not address a release issue.
3. Run a clean installation, lint, typecheck, unit suite, production build, and browser suite. If Windows blocks forked Vitest workers, use `npm test -- --pool=threads --maxWorkers=2`. Use Claude in Chrome when connected. Open a fresh session, test the main flow on desktop and mobile, open the labelled citation trap, correct the quote and citation metadata, and download the reviewed test copy. Check that Gemini failure, a missing Gemini key, and an unavailable registry all have a usable fallback. Use public demo inputs for live checks.
4. Stage an allow-listed release from audited project files. Confirm the build context excludes `.env.local`, private organiser PDFs, Git metadata, test output, downloaded projects, and unrelated files. Deploy to the team’s intended production host with HTTPS. Configure provider settings server-side through that host, using only credentials the owner authorised for it. A no-key release can use the clearly labelled sample and manual paths if those have been verified. Keep any existing repo visibility settings and paid plan unchanged.
5. Open the production URL in a clean browser session that has no host login. Run the core demo, confirm server routes and download work, and run the live smoke checks that apply to this configuration. Fix and redeploy if a release gate fails. Keep the previous deployment available for rollback when possible. Record the verified URL, release version, actual checks, known limits, and rollback target. Finish with the URL ready for the owner to share.
